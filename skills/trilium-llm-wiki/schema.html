What this is

This note is the schema of the LLM wiki: the conventions an AI assistant follows when it writes and maintains the pages under Wiki. Read it fully at the start of every wiki session, before touching any page. When you and the assistant agree on a new convention, change it here, not in a chat.

The pattern comes from Andrej Karpathy's "LLM wiki" idea: you curate sources, the assistant compiles them into a wiki of interlinked pages, and this schema keeps that work disciplined. Maintenance that humans abandon (cross-references, 15 pages touched per source) is the assistant's job.

Layout

  • Schema (this note, #llmWikiSchema): the rules.
  • Wiki (#llmWikiPart=wiki): everything the assistant writes. One child per topic, each topic a hub page with its concept and entity pages beneath it. Summaries sit under the topic they mostly belong to; use clones (a second parent) when a page belongs to several topics.
  • Sources (#llmWikiPart=sources, #readOnly inherited): raw material you add. Web clips, pasted articles, PDFs, files. The assistant reads these and never edits them; the one thing it adds is a fetched copy when you saved only a link (see Link-only sources). Organisation is by year only, since topics live in the wiki (see Sources layout).
  • Templates: one template per page type. Every wiki page is created from one of them, so the labels below are always present.
  • Views: saved searches that drive the workflows (pending sources, stubs, drafts, orphans, recent changes).
  • Log: the journal day note. Every ingest, query that produced a page, lint pass and other change to the wiki is recorded there (format below).

Sources layout

  • One folder per year directly under Sources (Sources/2026), marked #wikiSourceGroup=<year>.
  • Each direct child of a year folder is one source: a single note, or a folder when the source has parts (an article with its images, a PDF with notes, an exported notebook). Everything below it belongs to that source.
  • A summary's ~wikiSource points at that one note. The view Sources not yet summarised lists the direct children of Sources and of year folders that no summary points at yet.
  • You may drop a clip directly under Sources; on ingest the assistant moves it into the year it was added.

Link-only sources

A source that is little more than a URL (a bare link, an app's share text) cannot be summarised now or checked later. On ingest the assistant collects it:

  1. Fetch the page, preferably raw (curl or similar), and extract the article body from the HTML. Drop navigation, ads, cookie banners and related-article lists; do not reword, shorten or summarise the article. Keep images as links to their original URLs.
  2. Create one child note under the link note, titled Fetched copy, with the article as HTML and the labels #sourceUrl=<url>, #fetchedOn=<YYYY-MM-DD>, #fetchedVia=raw and #aiAssisted. The link note becomes the source folder and stays untouched; the summary's ~wikiSource still points at it.
  3. If only a processed fetch is available (a tool that returns a model's rendering of the page rather than the page), use it, set #fetchedVia=summary, and tell the user the copy is not the original wording.
  4. If the fetch fails or returns a paywall, login page or teaser, stop: tell the user, leave the source pending, and do not summarise from the title or URL.
  5. If the link note's title is share text rather than the article's title, suggest a better one; the user renames it.

The fetched copy is the only thing the assistant writes under Sources.

Page types and labels

Templates carry #wiki and #wikiType, which instances inherit, so #wiki finds every page. The promoted labels are set per page.

TypeTemplatePurposeLabels and relations
hubWiki Topic HubEntry point of a topic: what it covers, a curated list of its key pages, open questions.#wikiTopic, #wikiStatus
summaryWiki Source SummaryOne page per ingested source: key claims, data, quotes, how it relates to existing pages.~wikiSource (the raw note), #wikiTopic, #wikiStatus, #aiAssisted
conceptWiki ConceptAn idea, method, pattern or question, synthesised across sources, with citations to the summaries.#wikiTopic, #wikiStatus, #aiAssisted, ~relatesTo
entityWiki EntityA person, organisation, product, tool, place or dataset.#entityKind, #wikiTopic, #wikiStatus, #aiAssisted, ~relatesTo
  • #wikiTopic: short lowercase slug, the same as the hub's. One per topic the page belongs to (the label may repeat).
  • #wikiStatus: stub (title only, to be written), draft (written by the assistant, not yet reviewed), reviewed (you read and accepted it). Only you set reviewed.
  • #aiAssisted: present on anything the assistant wrote or substantially edited.
  • ~wikiSource: from a summary to its raw source note. This is how "sources not yet summarised" is computed, so it is mandatory on summaries.
  • ~relatesTo: a typed edge for connections worth showing in the note map that the body text alone does not make clear. Prefer inline links; use the relation sparingly.

Linking rules

  • Link generously between pages inside the body text. An internal link is <a class="reference-link" href="#root/<noteId>">Title</a>. Links are the graph; Trilium's note map and backlinks panel render them.
  • Cite claims by linking to the summary page of the source, not to the raw source.
  • When a concept or entity is mentioned that has no page yet, create a stub (from the template, #wikiStatus=stub, one sentence saying why it should exist) and link to it. Stubs are the to-do list.
  • Never duplicate: before creating a page, search #wiki by title and by #wikiTopic. Extend the existing page instead.
  • Every page must be reachable from a hub. New pages are linked from their hub's page list in the same ingest.

Writing rules

  • Bodies are HTML (Trilium text notes). Use headings, short paragraphs, lists and tables. No raw markdown.
  • Write for your future self: state the claim, then the evidence, then the open questions. Prefer concrete numbers and dates over adjectives.
  • Record disagreements. When a new source contradicts an existing page, do not silently overwrite: add a "Contradictions" section naming both sources and the dates.
  • Keep the raw source untouched. Quote it; do not reformat it.

Workflow: ingest

Trigger: "ingest", "process the sources", or a source added under Sources. Pending sources are the view Sources not yet summarised.

  1. If the source sits directly under Sources, move it into its year folder (create the folder with #wikiSourceGroup=<year> if missing).
  2. Read the raw source in full (and its attachments if any). If it is only a link, collect it first (see Link-only sources).
  3. Tell the user the three to five key takeaways and the topic(s) you would file it under. Wait for corrections if the user is present; otherwise continue.
  4. Find or create the topic hub. A new hub gets #wikiTopic=<slug> and #wikiStatus=draft.
  5. Create a summary page from the template under the hub, with ~wikiSource pointing at the raw note. Sections: Summary, Key claims, Data and quotes, Relevance, Open questions.
  6. Update every concept and entity page the source touches: add the new evidence with a link to the summary, note contradictions, create stubs for new concepts or entities. Expect 5 to 15 pages per source.
  7. Add the summary and any new pages to the hub's page list.
  8. Log it in today's journal note (format below): the summary, the hub, every page created or updated, the new stubs.
  9. Report: what was created, what was updated, which stubs now exist.

Workflow: query

  1. Search #wiki by topic and keywords; read the hub first, then drill into the pages it links.
  2. Answer with links to the pages and summaries the answer rests on. Say when the wiki has nothing on the question.
  3. If the answer required synthesis across several pages, offer to file it as a new concept page (status draft) so the exploration compounds. If filed, link it from the hub and log it.

Workflow: lint

Trigger: "lint the wiki", roughly weekly. Work through the views, fix what is mechanical, list what needs a human decision.

  1. Sources not yet summarised: offer to ingest them.
  2. Orphan pages: pages nothing links to. Link them from the right hub or propose deleting them.
  3. Stubs: pages with #wikiStatus=stub. Write the ones the existing summaries already support; list the rest as reading gaps.
  4. Drafts awaiting review: list them for the user; do not set reviewed yourself.
  5. Read each hub and check for contradictions between pages, stale claims, concepts mentioned without a page, and missing cross-links. Fix the mechanical ones, report the rest.
  6. Log it: each fix, and each open item for the user.

Log format

The day note has one <h2>Wiki</h2> heading, created on the first wiki action of the day and kept below whatever else is in the note. Under it is one list. Every action is one list item: the action word in bold (ingest, query, lint, adopt, move, cleanup, schema), then what happened, with links to the pages. Details go in a nested list, for example the pages created, updated and stubbed. Later actions on the same day are appended to the same list.

<h2>Wiki</h2>
<ul>
  <li><strong>ingest</strong>: Source title → <summary link>
    <ul>
      <li>Created: <links></li>
      <li>Updated: <links></li>
      <li>Stubs: <links></li>
    </ul>
  </li>
  <li><strong>lint</strong>: 4 fixes, 2 open items
    <ul><li>…</li></ul>
  </li>
</ul>

Human review

After every ingest, open the topic hub in Trilium's note map. Wrong edges, misfiled pages and bad topic slugs are cheapest to fix right then. Set #wikiStatus=reviewed on pages you have read and accept. The graph is the review step this system has instead of a compiler.
